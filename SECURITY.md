# Security and operational boundaries

The runtime is Bun/TypeScript with built-in fetch, crypto, filesystem and SQLite. There are no runtime npm dependencies. Pinned development tools are installed with scripts disabled. Build/test do not connect to Slack or Linear, install apps, register webhooks, start services, or change accounts.

Session credentials (`xoxc` and matching `d` cookie) have broad account power and are not a narrowly scoped sidebar grant. This tool never extracts credentials from browsers. Obtain account/organization authorization before any future live use, inject credentials through a local secret manager, and do not paste them into chat, config, commands, shell history, issue reports or logs. Bun may load a local `.env` automatically; ignore rules are not protection against accidental sharing. Prefer direct secret injection over credential files. Never enable shell tracing for secret injection. Revoke exposed credentials through the provider's controls.

Only fixed HTTPS provider hosts are used. Redirects are disabled. Bot requests use an Authorization header and no session cookie; internal requests use a form token plus only the matching `d` cookie. Linear reads use a separate API key. Errors omit response bodies and original exception text; unknown CLI flags are not echoed. There is no telemetry, message access, arbitrary API host configuration, dynamic plugin loading, or Linear mutation path. JSON plans/state still contain private entity/channel identifiers and section names; protect them accordingly.

Use a trusted private local state directory. New SQLite/lock files use 0600 and new directories use 0700. Existing file/directory permissions are not rewritten; audit them yourself before future use. State-file symlinks are refused, but ancestor-path substitution and hostile local filesystems are outside the trust model. The lock is a local process coordination aid, not distributed locking or a security boundary. Back up SQLite state with all writers stopped. A crash can leave a lock and pending intent; verify actual Slack state before recovery.

Apply is not atomic across services. Completed earlier writes remain if a later operation fails. No delete/archive/leave/rollback exists. Ambiguous channel creation persists an intent and blocks replay until inspected. A stale saved channel is an error, never an invitation to create a replacement or adopt a name collision. Readback verifies current membership under the tested response shape; it cannot establish an undocumented API's complete behavior.

Tests use fictional secrets and local temporary files only. Live credentials and real account data must never be added to test fixtures. Do not publish operational logs/state or reports containing credential material. Report security concerns privately through the repository owner's established channel; this document authorizes no message sending.
